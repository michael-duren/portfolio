This assumes you have the `nmcli` installed.

## 1. Identify the Ethernet interface

```bash
nmcli device status
```

**What it does:** Lists every network interface NetworkManager knows about — WiFi,
Ethernet, bridges, VPNs, etc. — along with its type and connection state.

**Why we ran it:** Needed to know the exact device name of the physical Ethernet
port plugged into the switch, since Linux doesn't always call it something intuitive
like `eth0`. In this case it was `enp3s0u2u2u3`. This naming convention is Linux's
"predictable network interface names" scheme, encoding bus/slot/port info — that's
why it looks cryptic compared to old-style `eth0`.

---

## 2. Create a static IP connection profile

```bash
nmcli connection add type ethernet ifname enp3s0u2u2u3 con-name udm-recovery ip4 192.168.1.25/24 gw4 192.168.1.1
```

**What it does:** Creates a _saved_ NetworkManager connection profile (not yet active)
called `udm-recovery`, bound specifically to the `enp3s0u2u2u3` interface.

**Why we specified a manual IP instead of using DHCP:**
A device in Recovery Mode doesn't run a DHCP server — it's a minimal bootloader-level
environment, not the full router OS. Normally when you plug into a router/UDM, _it_
hands your laptop an IP automatically via DHCP. In recovery mode nothing is offering
that, so your laptop has no way to get an address on its own. We had to manually put
the laptop on the same subnet (`192.168.1.x`) as the UDM's known recovery-mode
fallback address, or there'd be no way for the two devices to route traffic to each
other at all — like trying to mail a letter with no return address in the same zip code.

**Breaking down the flags:**

- `type ethernet` — this is a wired connection profile.
- `ifname enp3s0u2u2u3` — bind it to that specific physical interface.
- `con-name udm-recovery` — just a friendly label so we can reference/delete it later.
- `ip4 192.168.1.25/24` — manually assigns the laptop the address `192.168.1.25`,
  with a `/24` (i.e. `255.255.255.0`) subnet mask. The specific number `.25` was
  arbitrary — any unused address in `192.168.1.2`–`192.168.1.254` would've worked.
  It only matters that it's _in the same subnet_ as the device we're trying to reach.
- `gw4 192.168.1.1` — sets a default gateway. (This turned out to be the wrong
  address for where the UDM was actually listening — see step 4.)

**Why the specific IP "doesn't matter" here:** This was a closed, point-to-point
network — just the laptop and the UDM on an isolated switch segment, nothing else
handing out or claiming addresses. In a normal home/office network you'd have to
pick an IP carefully to avoid colliding with other devices or the DHCP pool. Here,
since nothing else was contending for addresses, almost any valid address in the
subnet would have worked identically.

---

## 3. Activate the profile

```bash
nmcli connection up udm-recovery
```

**What it does:** Switches the `enp3s0u2u2u3` interface over to actually use the
`udm-recovery` profile — this is the step that actually applies the static IP to
the interface (step 2 only _created_ the profile, it didn't apply it).

---

## 4. Test connectivity

```bash
ping 192.168.1.1
```

**Result:** Failed — `Destination Host Unreachable`. This specific error (not a
timeout) means the laptop couldn't even get an ARP response, i.e. nothing on the
local network claimed that address.

```bash
ping 192.168.1.30
```

_(after recreating the profile with the corrected gateway — see step 5)_

**Result:** Succeeded. This confirmed the UDM's recovery mode was actually
listening on `192.168.1.30`, not the more commonly referenced `192.168.1.1`.
Ubiquiti's docs list `.1` as the primary fallback and `.30` as secondary — this
device happened to be on the secondary.

---

## 5. Delete and recreate the profile with the correct gateway

```bash
nmcli connection delete udm-recovery
nmcli connection add type ethernet ifname enp3s0u2u2u3 con-name udm-recovery ip4 192.168.1.25/24 gw4 192.168.1.30
nmcli connection up udm-recovery
```

**What it does:** Removes the old profile (which pointed at `.1`) and recreates it
identically except pointing the gateway at `.30`, then reactivates it.

**Why recreate instead of edit:** Could have used `nmcli connection modify` to just
change the gateway field, but delete-and-recreate is simpler to reason about when
troubleshooting quickly — guarantees no leftover stale settings from the first attempt.

---

## 6. Root cause of the initial failure (not a command, but important)

The `.30` IP was actually correct the whole time — the real problem was that the
laptop was physically plugged into the wrong Ethernet port (a dock/hub port not
actually bridged to the switch). Once moved to the correct port, `.30` connected
immediately. This is a good reminder: when `ping` gives "Destination Host
Unreachable" rather than a timeout, it's often a link-layer problem (wrong port,
bad cable, switch config) rather than an IP/subnet mismatch.

---

## 7. Access the recovery web UI

```
http://192.168.1.30
```

Opened in a browser once ping succeeded — this loaded the UDM's Recovery Mode
interface, where we ran a filesystem check and uploaded firmware to reflash it.

---

## 8. After successful recovery — clean up the static profile

```bash
nmcli connection delete udm-recovery
```

**What it does:** Removes the manual static-IP profile entirely.

**Why:** Once the UDM finishes rebooting after a factory reset, it comes back up
as a normal router again — meaning **it now runs its own DHCP server** and expects
to be the one handing out addresses (typically starting from `192.168.1.1` as its
own address). Keeping a static `192.168.1.25` profile around would fight with that
DHCP server and cause IP conflicts, so we deleted it and let NetworkManager go back
to normal automatic DHCP behavior on that interface.

## Quick command cheat-sheet

| Command                                                                                   | Purpose                                             |
| ----------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `nmcli device status`                                                                     | List interfaces, find the Ethernet device name      |
| `nmcli connection add type ethernet ifname <if> con-name <name> ip4 <ip>/<mask> gw4 <gw>` | Create a static IP profile                          |
| `nmcli connection up <name>`                                                              | Activate a saved profile                            |
| `nmcli connection down <name>`                                                            | Deactivate a profile without deleting it            |
| `nmcli connection delete <name>`                                                          | Remove a saved profile entirely                     |
| `ip addr show <if>`                                                                       | Confirm what IP is actually applied to an interface |
| `ping <ip>`                                                                               | Test basic Layer 3 reachability                     |
